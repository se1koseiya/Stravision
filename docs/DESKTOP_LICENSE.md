# 附：桌面端授权码机制（技术实现）

> 上半部分是面向用户的许可协议，本部分是面向运维/开发的技术说明。
> 目标：**用授权码控制桌面端"能不能用、能用到哪天"**，且管理员随时可改。

## 1. 机制概览

| 维度 | 设计 |
| --- | --- |
| 码格式 | `STV-XXXX-XXXX-XXXX-XXXX`，Crockford Base32（剔除 I/L/O/U），16 个有效字符 ≈ 80 bit 随机性 |
| 绑定 | **一码一机**：首次激活时把设备指纹写进激活记录；换机需后台解绑 |
| 有效期 | 由后台控制，支持「指定到期日 / 从现在起 N 天 / 永久」；改完客户端**下次心跳即生效** |
| 校验 | 联网校验为主（`https://stravision.site`），离线**宽限 7 天**（可按码调整，见 §11） |
| 离线 | 管理员可用本机私钥签发「离线授权串」，客户端粘贴即用、不联网（见 §11） |
| 防伪 | 服务端 Ed25519 私钥签发「租约」，桌面端内置公钥验签 —— 离线状态下也无法伪造或续期 |
| 吊销 | 后台「停用」→ 客户端下次心跳被拒（403）→ 本地授权作废，下次启动要求重新激活 |

## 2. 激活与续期时序

```
桌面端启动
  ├─ evaluate() 本地判定（不发网络请求）
  │    ├─ 无本地授权 / 已过期 / 超宽限 / 租约验签失败 → 弹「激活本机」窗口
  │    └─ 有效 → 放行，继续启动（并后台异步心跳）
  │
  └─ POST /api/license/activate   { code, deviceId, deviceName, platform, appVersion }
       └─ 服务端校验：码存在 → 未停用 → 未过期 → 设备名额未满
          ├─ 通过 → 登记激活 + 签发租约 → 桌面端验签后落盘 → 放行
          └─ 拒绝 → 激活窗口显示原因，停留等待重输

运行期（每次启动 + 每 6 小时）
  └─ POST /api/license/heartbeat  { code, deviceId, appVersion }
       ├─ 服务端状态有变（续期/停用/解绑）→ 换发新租约 → 桌面端刷新本地缓存
       ├─ 网络不可达 → 什么都不做，由 7 天离线宽限兜底
       └─ 服务端明确拒绝（403/404）→ 本地授权作废，下次启动要求重新激活
```

**为什么启动不被网络阻塞**：客户机房常年断网，一断网就用不了不可接受。
因此本地租约有效就先放行，联网结果只用于"收紧"（作废）而不用于"放开"。

## 3. 数据表

两张表在 `lib/db/database.ts` 的 `initDB()` 里幂等创建：

- **`desktop_licenses`** —— 签发的授权码
  `code`（唯一）、`label`（备注/客户）、`status`（`active`/`revoked`）、
  `max_activations`、`expires_at`（毫秒时间戳，NULL = 永久）、`created_by`、`created_at`、`updated_at`
- **`desktop_license_activations`** —— 设备激活记录
  `license_id`、`device_id`（指纹）、`device_name`、`platform`、`app_version`、
  `status`（`active`/`released`/`revoked`）、`ip`、`activated_at`、`last_seen_at`
  唯一索引 `(license_id, device_id)`：同一台机器重复激活走 upsert，不占额外名额。

## 4. 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/license/activate` | 公开（限流 10 次/分/IP） | 授权码 + 设备指纹 → 租约 |
| POST | `/api/license/heartbeat` | 公开（限流 60 次/分/IP） | 确认有效 + 换发最新租约 |
| GET | `/api/admin/desktop-licenses` | admin / super_admin | 列表（含激活数）；`?withActivations=1` 附带设备明细 |
| POST | `/api/admin/desktop-licenses` | admin / super_admin | 签发 |
| PATCH | `/api/admin/desktop-licenses` | admin / super_admin | 改期 / 续期 / 停用 / 改备注 / 改台数 |
| DELETE | `/api/admin/desktop-licenses?id=` | admin / super_admin | 删除（连带清激活记录） |
| GET | `/api/admin/desktop-licenses/activations?licenseId=` | admin / super_admin | 查看已激活设备 |
| POST | `/api/admin/desktop-licenses/activations` | admin / super_admin | 解绑设备（`{ activationId }`） |

续期语义（PATCH 三选一）：
- `{ permanent: true }` → 永久有效
- `{ durationDays: 365 }` → 从现在起重新计 365 天
- `{ extendDays: 30 }` → 在原到期日基础上顺延 30 天（已过期则从今天起算）
- `{ expiresAt: 1767225600000 }` → 直接指定到期时刻

## 5. 后台操作

管理后台 → **系统管理 → 桌面端授权**：

1. **签发授权码** → 填备注、选有效期（按天数 / 指定到期日 / 永久）、填可激活台数 → 得到码，复制发给客户。
2. **改期** → 行内「改期」→ 选「在原到期日顺延 N 天」即可续期；改完提示客户重启应用。
3. **停用 / 恢复** → 行内「停用」；停用后客户端下次心跳被拒，本地授权作废。
4. **查看设备 / 解绑** → 点「激活设备」列 → 看到设备名、平台、版本、最后活跃时间，可解绑腾出名额。
5. **删除** → 删除不可恢复，已激活客户端会全部失效。

## 6. 部署步骤

### 6.1 生成签名密钥（只做一次）

```bash
pnpm desktop:license:keys        # 等价于 node scripts/desktop/generate-license-keys.mjs
```

产出：
- `data/desktop-license-keys.json` —— 私钥+公钥（已 gitignore，**不要提交**）
- `desktop/lib/license-public-key.js` —— 桌面端内置公钥（可提交）
- 终端打印两条环境变量

### 6.2 服务端注入私钥

在服务器 `.env` 写入（值来自上一步终端输出）：

```
DESKTOP_LICENSE_PRIVATE_KEY=<base64 PKCS8>
DESKTOP_LICENSE_PUBLIC_KEY=<base64 SPKI>
```

⚠️ 私钥绝不能硬编码进源码：桌面端与 Web 端是同一份代码，路由会被一起打进安装包。

> **这一步是可选的**：如果你只打算用「离线授权串」（§11.2）发授权，
> 服务端不配私钥也完全可用 —— 代价是失去在线激活、心跳改期与远程吊销能力。

### 6.3 重新打包并分发桌面端

```bash
pnpm desktop:pack:win     # = desktop:build + electron-builder（见 docs/DESKTOP.md）
```

公钥已随 `desktop/lib/license-public-key.js` 打进安装包。上传 `release/` 下的
`Stravision-<版本>-win-x64.exe` + `.blockmap` + `latest.yml` 到
`https://stravision.site/downloads/desktop/`。

> 已有的旧版本安装包**没有**授权校验代码，仍可正常使用；授权只对本次及之后打包的版本生效。

### 6.4 验证

```bash
pnpm desktop:verify:license    # 租约验签 / 篡改拒绝 / 过期与宽限 / 换机 判定
```

## 8. 排障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 启动即弹「激活本机」 | 从未激活，或本地授权已失效 | 输入授权码；若提示已停用/过期，在后台处理 |
| 提示「授权码不存在」 | 输错 / 已被删除 | 核对大小写与分组；O→0、I/L→1 会自动纠正 |
| 提示「已达到激活上限」 | 该码已绑满设备 | 后台解绑旧设备，或改大 `maxActivations` |
| 提示「已超过 7 天未联网校验」 | 长期离线 | 联网后重启应用（会自动心跳刷新） |
| 提示「客户端缺少授权公钥」 | 打包时漏注入公钥 | 重新执行 6.3 打包 |
| 客户说改了期还没生效 | 心跳未跑到 | 重启应用，或等下一次心跳（≤6 小时） |
| 客户换机后无法激活 | 名额被旧机占用 | 后台解绑旧设备 |

## 9. 安全边界（如实说明）

- 租约用 Ed25519 非对称签名，客户端只有公钥 → **改本地文件、自建假服务器都无法伪造或续期**。
- 授权服务地址硬编码为 HTTPS 公网地址（`STRAVISION_LICENSE_SERVER` 可覆盖，仅用于自测）。
- 但要清楚：**客户端软件没有绝对不可破解的方案**。能拿到安装包的人原则上也能逆向并改掉校验分支。
  本机制的目的是把"随手就能白嫖/无限续期"抬到"需要相当成本的专业破解"，
  并把商业客户纳入可追踪的授权管理（谁在用、用在哪台、用到哪天）。
- 如需更强约束（如核心功能上云、按量计费），应把关键能力放到服务端而非客户端。

## 11. 服务器解耦：A 离线宽限可调 / B 离线授权串

> **背景**：授权校验依赖 `https://stravision.site`。服务器一旦停机、到期，或域名失效，
> 就会陷入「新机无法激活 + 老机在最后一次联网成功 7 天后锁死」。
> 本章两项能力把**授权体系与服务器寿命解耦**，且不需要改动服务器。

### 11.1 A —— 离线宽限天数可按码设置

原设计中宽限固定 7 天，且**与是否为永久码无关**：只要 7 天连不上服务器就锁死。
现在宽限天数写进**签名租约**的 `gd` 字段，由后台按码设置：

| 客户情况 | 建议宽限 |
| --- | --- |
| 常规客户（能上网） | 7 天（默认） |
| 网络不稳 / 偶尔断网 | 90 天 |
| 装完就长期断网、不会再联网 | **3650 天（≈永久）** |

- 后台位置：签发弹窗与改期弹窗里的「离线宽限天数」，列表中有独立列显示。
- 客户端读的是**已验签的租约**，改不了；不带 `gd` 的旧租约按 7 天处理（向后兼容）。
- 宽限只解决「连不上服务器」，**不解决「授权过期」** —— 到期时间照旧生效。

### 11.2 B —— 离线授权串（服务器不可用也能发授权）

完全不经过服务器：用**本机那份私钥**签发一张绑定指定设备指纹的租约，客户粘贴即用。

**流程**

1. 客户在「激活本机」窗口点「复制」，拿到 64 位设备指纹发给你；
2. 任选一种签发方式：
   - **后台**：系统管理 → 桌面端授权 → 「生成离线授权」→ 填指纹 + 有效期 → 复制授权串；
   - **命令行**（不依赖服务器，服务器已停机时用这个）：
     ```bash
     pnpm desktop:license:offline --device <64位指纹> --days 365 --label "张三 · 1号大棚"
     # 可选项：--expires 2027-12-31 / --permanent / --out license.txt / --json
     ```
3. 把整串发给客户，让他在激活窗口切到「离线授权串」标签粘贴 → 完成（纯本地验签）。

**与在线码的差异（关键）**

| 维度 | 在线授权码 | 离线授权串 |
| --- | --- | --- |
| 激活 | 联网向服务器换取租约 | 本地验签，**不发任何网络请求** |
| 心跳 | 每 6 小时 | **跳过**（该码不在服务端库里，发心跳只会拿到 404 被误判失效） |
| 离线宽限 | 按 `gd` | **不适用**，有效期只看到期时间 |
| 远程改期 / 吊销 | ✅ | ❌（签发后无法撤回） |
| 服务器停机后 | 宽限用尽即失效 | **完全不受影响** |

**安全边界**：离线串同样由 Ed25519 私钥签名，客户端只有公钥 ——
无法伪造、无法篡改到期时间、也无法把签给别人的串用在自己机器上（指纹不匹配会被拒）。
代价是**无法远程吊销**，这是「完全脱钩服务器」的必然取舍。
拿不准的客户优先用在线码；长期断网 / 服务器不可用的客户用离线串。

### 11.3 部署上的含义

- **服务器可以完全不动**：只用离线串时，服务端 `.env` 没有私钥也照样能用；
- 打包前必须先跑 `pnpm desktop:license:keys`（公钥会打进安装包），否则客户端会报「缺少授权公钥」；
- 私钥文件 `data/desktop-license-keys.json` 就是你的**签发权**：备份好、别丢、别外传。
  一旦丢失，既不能再签发离线串，服务器也无法签发租约（只能重新生成密钥对并重新打包分发）。

## 12. 本地授权码控制台（不依赖服务器地"控制码"）

离线串不进服务端库，所以「签了什么、给了谁、哪个快到期」必须有地方记 —— 否则两星期后你自己也说不清。
控制台把这件事收回到**你自己的电脑**上：私钥不出本机，台账落本地文件，全程零网络。

### 12.1 两个文件

| 文件 | 作用 |
| --- | --- |
| `data/desktop-license-keys.json` | 私钥（0600）= 签发权，**别丢别外传** |
| `data/desktop-license-vault.json` | 台账（0600）：码 / 设备指纹 / 备注 / 到期 / 授权串 / 操作历史 |

台账写入走「临时文件 → rename」，写一半被杀也不会损坏。

### 12.2 命令

```bash
pnpm license issue --device <64位指纹> --label "张三 · 1号棚" --days 365
pnpm license issue --devices devices.txt --days 365     # 批量（每行 `<指纹> [备注]`）
pnpm license list [--all|--expired|--revoked|--json]    # 台账
pnpm license show <码|序号>                              # 详情（含操作历史）
pnpm license export <码|序号> [--out f]                  # 重取授权串（客户弄丢了可重发）
pnpm license renew <码|序号> --days 365                  # 续期（在原到期日上顺延）
pnpm license revoke <码|序号> --reason "…"               # 台账标记作废
pnpm license stats                                       # 统计
pnpm license:ui [--port 5188]                            # 网页控制台（只监听 127.0.0.1）
```

网页控制台 = 同一个台账的可视化界面：签发 / 搜索 / 取串 / 续期 / 作废，启动后自动开浏览器。

### 12.3 边界：这里的"作废"不是远程吊销

⚠️ 台账里的 `已作废` 只是**本机的一条备注**。客户端永不联网，收不到它 ——
客户机上的串会一直用到 `exp` 到期。真要止损只有两条路：

1. **不续期**（推荐）：短周期签发（90 / 180 天），到期必须回来找你重签 —— 这就是你的控制力；
2. **换密钥**（核弹）：`pnpm desktop:license:keys --force` 重新生成密钥对 → 所有旧租约验签失败，
   但必须**重新打包并让所有客户更新客户端**，代价极大，只在私钥泄露时考虑。

### 12.4 真正的远程吊销：拉取式（已实现，见 §13）

物理前提：客户端至少偶尔要能上一次网。平台里的 AI 功能本来就必须联网，
所以这个前提对真实客户成立 —— 完全离线的机器则只能靠换密钥。

清单**不放在自己的服务器上**，而是任意静态托管（Gitee / GitHub raw、Pages、COS、R2）：
服务器在不在跟它无关。详见 §13。

## 13. 拉取式吊销（没有服务器也能作废已发出的码）

### 13.1 它是什么

管理员手里有一份**用私钥签名的「作废清单」**，内容就是一串被作废的授权码。
把它原样上传到一个静态托管（Gitee raw / GitHub raw / Pages / 腾讯云 COS / Cloudflare R2 —— 免费、稳定、
不需要你运维任何服务器），客户端每隔一段时间去拉一次：命中自己的码 → **锁死**。

因为清单本身带 Ed25519 签名，托管方（哪怕被入侵）也造不出能通过验签的假清单，
最多只能把旧清单再发一遍（回滚），这个由比对 `t` 时间戳拦下。

### 13.2 三步走

```bash
# ① 一次性设置（清单直链 + 复检周期；之后签的码都会带上）
pnpm license config --rl https://gitee.com/<你>/raw/revoked.json --rk 30

# ② 作废某个码（自动重建 data/desktop-revocation.json）
pnpm license revoke STV-XXXX-XXXX-XXXX-XXXX --reason "欠费"

# ③ 把清单内容上传到 ① 那个地址
pnpm license revocation      # 打印可直接上传的那一行
```

对**已经签出去、当时没配 rl** 的码：
`pnpm license renew <码> --rl <清单直链>` 重签一次即可（反正是要重发新串给客户的）。

### 13.3 客户端怎么判定

| 情况 | 状态 | 行为 |
| --- | --- | --- |
| 清单里没有本机码 | `active` | 正常用，记下本次复检时间 |
| 清单里命中本机码 | `revoked` | **永久锁死**（重新导入新串才解） |
| 拉不到（断网 / HTTP 5xx / 托管挂了） | 维持原状 | **不误杀**，交给超期窗口兜底 |
| 超过 `rk + gd` 天没成功复检 | `revocation-overdue` | 要求联网后重启 |
| 租约没写 `rl` | `active` | 纯离线串，永不联网（向后兼容） |

- 启动即复检一次；运行期每 6 小时再复检一次（不重启也能在半天内生效）。
- 运行期命中会弹窗说明并退出应用。
- 判定窗口：默认 `rk=30` 天复检一次，`gd`（离线宽限，默认 7）天缓冲 → **断网 37 天内不会误杀**。

### 13.4 相关文件

| 文件 | 作用 |
| --- | --- |
| `desktop/lib/license.js` | `checkRevocation()` / `verifyRevocationList()` / `evaluate()` 的 `revoked`、`revocation-overdue` 判定 |
| `desktop/lib/license-config.js` | 打包期内置的清单地址（留空 = 只有带 `rl` 的码才检查；填上则**老码也一起管**） |
| `desktop/main.js` | `ensureLicensed()` 启动复检 + `startRevocationTimer()` 运行期复检 |
| `scripts/desktop/verify-revocation.cjs` | 端到端回归：`pnpm desktop:verify:revocation`（23 项） |

### 13.5 回归覆盖

`pnpm desktop:verify:revocation` 用一个临时 userData + 本地 HTTP 服务跑完整链路，
不碰真实台账与真实清单文件。覆盖：清单验签（正常 / 篡改 / 他人密钥 / 垃圾串）、命中锁死、
未命中放行、无 `rl` 跳过、网络不可达与 HTTP 500 不误杀、超期判定、防回滚、重新导入解除锁死。

### 13.6 抗篡改加固（客户端侧）

默认 `pnpm desktop:pack:win` 会走三层加固（排障时加 `--no-obf` 可打未混淆版本对比）：

| 层 | 做法 | 挡住什么 |
| --- | --- | --- |
| ① 代码混淆 | `scripts/desktop/obfuscate-desktop.mjs`：把 `desktop/` 复制成 `desktop-obf/`，混淆 `main.js` 与 `lib/license*.js`、`lib/secrets.js`（字符串 rc4 加密 + 压缩，保留 require 路径与属性名），再拿它当 appDir | `asar extract` 后读不到授权逻辑、公钥、IPC 通道名 |
| ② Fuses | `desktop/after-pack.cjs`（afterPack 钩子）烧进二进制：`OnlyLoadAppFromAsar` + `EnableEmbeddedAsarIntegrityValidation` + 禁用 `--inspect`/`NODE_OPTIONS` | **改 app.asar 里的任何字节 → 完整性校验失败 → 应用起不来** |
| ③ 公钥指纹自检 | `desktop/lib/license-public-key.js` 里带 `fingerprint = sha256(publicKey)`，客户端加载时比对 | 把内置公钥换成自己生成的那把（最省事的绕过手法） |

**它挡不住什么**（如实说，别指望银弹）：

- 有耐心的逆向：混淆与完整性校验都只是提高门槛，不是加密级保护；
- **整包重新打包并自己分发**：这要靠代码签名证书（Windows Authenticode / OV 证书，年费几百到几千）。
  没有证书时，任何人都可以解包 → 改 → 重新烧 fuses → 分发。
  目前 NSIS 安装包未签名，SmartScreen 也会报"未知发布者"。
- 授权体系的真正兜底是**联网**：客户端会定期核对吊销清单，被破解的客户端可随时作废。

**相关文件**：`scripts/desktop/obfuscate-desktop.mjs`、`desktop/after-pack.cjs`、
`desktop/lib/license.js`（`loadBuiltinPublicKey` 的指纹比对）、
`desktop/verify-packaged.mjs`（`[2b]` 段会断言产物确实混淆过）。

### 13.7 用 Gitee raw 托管（一键发布）

准备两样东西：

1. 一个**公开**仓库（私有仓库的 raw 链接会跳登录页，客户端拉到的是 HTML）；
2. Gitee 私人令牌（设置 → 私人令牌，勾选 `projects` 写权限）。

```bash
# 首次（配置存 data/desktop-publish-gitee.json，0600，已被 .gitignore 忽略）
pnpm license:publish --repo <owner>/<repo> --token <令牌> --set-rl

# 日常：作废 → 一键上传 → 自动校验客户端视角能否拉到
pnpm license revoke STV-XXXX-XXXX-XXXX-XXXX
pnpm license:publish

# 只校验线上那份（改完仓库可见性 / 排查"为什么没生效"时用）
pnpm license:publish --check
```

`--set-rl` 会把 raw 直链（`https://gitee.com/<owner>/<repo>/raw/<branch>/revoked.json`）
写进签发的默认配置，之后签的码自动带上。

**Gitee raw 的两个坑**

- **必须公开仓库**：私有的话 `fetch` 拿到的是登录页，`--check` 会直接告诉你这个原因；
- **有 CDN 缓存**：上传后几分钟内客户端可能仍拉到旧清单。急用就在客户端等下一次复检，
  或改用腾讯云 COS / Cloudflare R2（可设 `Cache-Control: no-store`）。

清单里只有授权码，没有客户姓名、设备指纹等敏感信息，公开仓库可接受。

**当前托管**（2026-09-29 起）

- 仓库：<https://gitee.com/guantougitee/berryrealmrecord>（公开）
- raw 直链：`https://gitee.com/guantougitee/berryrealmrecord/raw/master/revoked.json`
- 发布配置（含令牌）：`data/desktop-publish-gitee.json`（0600，不进 git）

  上传后 raw 的 CDN 约 1~2 分钟才刷新，脚本会提示"等几分钟再验"。
