# 病虫害视觉诊断能力方案

> 结论先行：**平台的视觉链路其实已经通了 80%，真正的问题不是「没有视觉能力」，而是「视觉能力没被组织成诊断业务」。**
> 用户传一张病叶照片，图能进模型、模型也能看图 —— 但它走的是开放式闲聊，输出的是散文，不是可核对、可呈现、可沉淀的诊断结论。

---

## 一、结论（TL;DR）

| 维度 | 判断 |
|---|---|
| 图片上传 → 传模型 | ✅ 已具备，无需重做 |
| 视觉模型自动路由 | ✅ 已具备（`supportsVision`） |
| 结构化诊断端点 | ⚠️ 存在但是「生长巡检」语义，不能直接当病虫害用 |
| **病虫害诊断协议**（病名/置信度/严重度/防治） | ❌ **缺失 —— 这是核心缺口** |
| **诊断结果卡片** | ❌ 缺失（现有 VisionCard 是摄像头巡检，不是用户上传图） |
| **结果闭环**（病历沉淀 / 知识溯源 / 自动巡检） | ❌ 缺失 |
| 图片在历史会话中保留 | ❌ 有 bug（会被 `String()` 毁掉） |

**方案主线**：不去重造视觉能力，而是在已有链路上**新增 3 个东西** ——
① 统一「视觉诊断网关」② 面向病虫害的结构化诊断协议 ③ DiagnosisCard 呈现卡片，
再分三期把「病历沉淀 → 知识溯源 → 自动巡检」的闭环补齐。

**P0 工作量**：新增 4 个文件、改 3 个文件，**不触碰** `/api/chat` 主链路与 provider 层。

### 2.2 真实缺口

1. **「病虫害识别」胶囊是"假"的**
   `components/ai/farm-skills.tsx:49-73` —— 它只把一段文字 prompt 灌进输入框，**并不消费用户上传的图**。用户传了照片，图和胶囊提示词各走各的，模型自由发挥，输出不可控、无法卡片化。

2. **没有面向病虫害的结构化协议**
   `PlantAnalysisResult`（`lib/types/plant-growth-types.ts:17`）只有 `stage / healthScore / issues / recommendations / heatmap` —— **没有病名、没有置信度、没有严重度分级、没有鉴别排除、没有防治分级**。这不是诊断，是巡检评分。

3. **没有诊断结果卡片**
   已有 `VisionInspectionCard`（摄像头云台巡检用）和 `DecisionCard`，但没有「用户上传图 → 诊断结论」的卡片。

4. **`/api/vlm/analyze-frame` 有三个硬伤**
   - 单图、单轮、固定 prompt，无法承载「全株 + 病部特写」多图鉴别；
   - **自写 apiKey/apiUrl**（`:14-23`），违反项目铁律「AI 辅助接口必须复用主对话模型链路（`readProvidersConfig` → `resolveDefaultModelId` → `resolveProvider`）」；
   - 硬编码默认模型 `qwen3-vl-plus`，与用户的 provider 配置脱节。

5. **历史会话丢图**
   `app/api/sessions/[id]/route.ts:36-42` 用 `String(m.content)` 落库 —— 多模态数组被字符串化，**刷新会话后图片全丢**。

6. **无知识溯源 / 无对象存储 / 自动巡检是占位**
   `lib/mqtt-service.ts:1018` 只执行 `trigger_type === 'sensor'`，`trigger-node.tsx:59` 的 `vlm` 病害触发是纯 UI 占位。

### 2.3 ⚠️ 一个被忽略的产品级风险

通用 VLM（qwen-vl / gpt-4o / glm-4v）在**细粒度农业病害**上并不可靠：
早期病斑、螨类（红蜘蛛）、虫卵、营养失调与病毒病的外观高度相似，**单张远景照片的准确率会显著低于用户的心理预期**。
→ 所以方案的重点不是"换个更强的模型"，而是**用工程手段兜住模型的短板**（见第六节）。

## 三、目标架构：四层链路

```
① 采集层  →  ② 感知层  →  ③ 呈现层  →  ④ 闭环层
 图片进来     结构化诊断     诊断卡片      沉淀与复用
```

- **① 采集层**：在已有上传能力上补「拍摄引导」和「局部裁剪放大」—— 因为**拍得对**比模型强更重要。
- **② 感知层**：新建统一 `vision-gateway`，把「模型选择 + 多图组装 + 结构化协议 + 解析校验 + 置信度」收敛到一个模块，任何视觉需求都走它。
- **③ 呈现层**：沿用项目成熟的 tag 卡片协议，新增 `DiagnosisCard`（病名 / 置信度环 / 严重度 / 图中依据 / 鉴别排除 / 四级防治）。
- **④ 闭环层**：诊断结果沉淀为「病历」，反哺知识库与自动巡检。

## 四、P0 落地清单（可执行，文件级）

> 目标：打通一条**可控、可呈现、可沉淀**的病虫害图像诊断主链路。

### 4.1 新增文件

| 文件 | 职责 |
|---|---|
| `lib/ai/vision/vision-gateway.ts` | 统一视觉诊断入口。入参 `{ images: string[], scene: 'disease'\|'growth', context?: {...} }`，内部**复用** `readProvidersConfig → resolveDefaultModelId → resolveProvider` 选视觉模型、复用 `adaptChatRequestBody`，支持多图，返回已校验的 `DiagnosisResult`。 |

## 五、P1 / P2 演进

### P1 —— 把准确率和体验拉起来
1. **多图鉴别**：引导用户拍「全株 + 病部特写」两张，网关并发送图，显著提升细节识别率。
2. **低置信追问**：`confidence < 0.6` 时不硬给结论，卡片直接输出「建议补拍叶背 / 果实特写」。
3. **修历史丢图**：`sessions/[id]/route.ts` 改为保留结构化 content（或附件单独存），补 `data/sessions.json` 的迁移兼容。
4. **病历沉淀**：新增 `plant_diagnosis_records` 表（`lib/db/database.ts` 原生 SQL 风格），存图片 URL + 结构化结果 + 地块/棚区，支撑「同一棚区病害趋势」。

### P2 —— 规模化闭环
5. **病害知识库 RAG**：防治方案不再靠模型幻觉，从知识库检索（项目已有 `knowledge_*` 体系）并给出出处。
6. **自动巡检**：为 `lib/mqtt-service.ts` 补 `trigger_type === 'vlm'` 执行器，让摄像头定时抓帧 → 网关诊断 → 异常才推送，形成真实闭环。
7. **对象存储 + 专用模型**：图片上云（COS/OSS/S3 任一）+ 累积标注数据后，评估自训/微调轻量分类模型作为「快筛」，VLM 只做疑难复核。

## 六、关键决策：准确率怎么提（这节最重要）

不要把希望压在「换个更强的视觉模型」上。正确做法是**用工程手段兜住模型短板**：

| 手段 | 为什么有效 |
|---|---|
| **结构化鉴别诊断**（给候选 + 排除理由 + 置信度），而不是"描述一下" | 迫使模型做鉴别而非泛泛而谈，同时让用户能核对 |
| **强制要求 `evidence`（图中依据）** | 有依据可查 = 幻觉无处藏身；也是可信度的天然门槛 |
| **引导拍摄（先问部位、要特写）** | 用户随手一张远景照，模型"看不见"细节；**拍得对比模型强更关键** |
| **多图输入（全株 + 局部）** | 尺度互补，是提准确率性价比最高的一招 |
| **领域先验（草莓常见病害清单 + 诱发条件）** | 复用 `farm-skills.tsx:63-68` 已有的病害知识（白粉/灰霉/炭疽/红蜘蛛/蚜虫），把先验写进 prompt |
| **置信度阈值 + 追问** | 不确定就说不确定，比给错药方安全得多 |
| **四级防治优先级**（环境调控 → 物理 → 生物 → 化学） | 与平台既有「绿色防控」品牌调性一致，且规避直接开药方的合规风险 |

⚠️ **合规红线**：化学药剂建议必须包含**安全间隔期**与"以当地植保部门为准"的免责表述，避免农药推荐责任。

## 七、验收标准

- **功能**：上传病叶图 → 3~8s 内返回结构化诊断 + 卡片渲染（含病名/置信度/严重度/依据/防治四级）。
- **协议**：`DiagnosisResult` 通过 JSON Schema 校验；解析失败有降级文案，不白屏。
- **链路**：`/api/vlm/analyze-frame` 与 `vision-gateway` **共用**模型解析逻辑（grep 确认无第二处硬编码模型名）。
- **不走样**：`npx tsc --noEmit` 无新增错误（项目基线 330+，只看增量）。
- **视觉**：卡片在明/暗双主题下用 CDP 探针锁 `Emulation.setEmulatedMedia` 复验（注意 Tailwind v4 颜色是 `lab()`/`oklab()`，断言前先归一化）。
- **不回归**：摄像头 VisionInspectionCard 巡检流程不受影响（`PlantAnalysisResult` 出参保持不变）。

## 八、风险与铁律约束

| 风险 | 对策 |
|---|---|
| 图片 base64 内联导致请求体过大 | P0 沿用现有 10MB 限制 + 前端压缩（复用 `camera-capture.ts` 的自动降质思路） |
| 视觉调用成本翻倍 | 走独立端点而非对话内工具，单次调用；P1 再加工具化 |
| 模型返回非法 JSON | 复用 renderer 的 `tryParseJsonWithRepair` 思路，网关侧也做一次修复 |
| 用户误把「疑似」当「确诊」 | 卡片固定展示置信度 + 免责提示；低置信强制追问 |
| 破坏既有链路 | P0 不碰 `/api/chat`、provider 层、`plant-growth-types.ts` |
